# 팀 지식 중앙화 플러그인 (kc-plugin) 설계

- 날짜: 2026-07-22
- 상태: 설계 확정 (구현 계획 전)

## 1. 목적

코드·PPT·문서 등 모든 팀 작업의 **사고의 흐름**(왜 이 결정을 했는지, 어떤 대안을 시도하고 버렸는지, 무엇이 미해결인지)을 git 기반 Obsidian vault에 중앙화한다. 코드와 산출물 자체는 Claude Code로 파악 가능하지만 프로젝트의 맥락은 전달이 어렵다 — 이 플러그인은 그 맥락을 기록·관리·제공하여 **새 팀원이 프로젝트에 soft landing** 할 수 있게 한다.

PPT·문서 생성기가 아니다. PPT·문서는 "제작 과정의 컨텍스트가 기록되는 대상"이다.

## 2. 범위와 단계별 확장 전략

- **1단계 (이 설계의 범위)**: 순수 Claude Code 플러그인. 개발자 팀원에게 먼저 배포. 비개발자는 Obsidian `inbox/` 폴더로 참여
- 2단계 (추후): MCP 서버를 얹어 비개발자가 Claude 앱에서 직접 기여
- 3단계 (추후): self-hosted git의 CI로 큐레이션 자동화

vault는 모든 단계에서 "순수 git repo + 마크다운"이므로, 단계 확장 시 기존 지식과 구조가 그대로 유지된다.

### 전제 조건

- vault repo는 **self-hosted git** — 순수 git 명령만 사용 (gh CLI, GitHub API 금지)
- 개발자 팀원은 Claude Code 사용, 비개발자는 Obsidian + Claude 앱 사용 가능
- 노트와 문서는 한국어 작성

## 3. 아키텍처

두 개의 git repo로 구성:

### ① 플러그인 repo (`kc-plugin`) — 개발자가 Claude Code에 설치

```
kc-plugin/
├── .claude-plugin/plugin.json    # 플러그인 매니페스트
├── skills/
│   ├── kc-setup/                 # /kc:setup   — 최초 설정 (vault clone, 경로·이름 등록)
│   ├── kc-log/                   # /kc:log     — 수동 컨텍스트 기록 (인터뷰식)
│   ├── kc-review/                # /kc:review  — 대기열 초안 검토 → 승인 → vault 반영
│   ├── kc-sync/                  # /kc:sync    — 읽기 동기화·상태 진단·복구
│   ├── kc-curate/                # /kc:curate  — inbox 처리, 링크·인덱스 정비, 승격
│   ├── kc-onboard/               # /kc:onboard — 프로젝트 온보딩 브리핑
│   └── kc-ask/                   # /kc:ask     — vault 질의응답
├── hooks/
│   ├── commit-capture.sh         # 커밋 감지 → 기록 제안 신호 (주 트리거)
│   └── session-capture.sh        # 세션 종료 → 대기열 등록 (안전망)
└── templates/                    # 컨텍스트 노트·topic 노트·_index 템플릿
```

각 팀원 머신에는 `/kc:setup`이 생성하는 로컬 설정 파일(vault 경로, git remote, 작성자 이름, 등록된 프로젝트 목록)만 존재한다. 모든 명령이 이 설정을 읽어 동작한다.

### ② Vault repo — 팀 공유 지식 저장소

- 개발자: 플러그인이 git으로 읽고 씀
- 비개발자: Obsidian(+ 아무 git 클라이언트)으로 직접 열람, `inbox/`에 기여

## 4. Vault 구조

```
vault/
├── projects/
│   └── <프로젝트-슬러그>/
│       ├── _index.md             # 프로젝트 MOC: 목적, 현재 상태, 주요 결정 링크
│       └── context/
│           └── YYYY-MM-DD-<주제>.md
├── topics/                       # 프로젝트 간 공통 주제 — 연관 관계의 허브
│   └── <주제>.md
├── inbox/                        # 비개발자·자유형식 투입 (큐레이션이 처리)
└── _meta/
    ├── conventions.md            # vault 규칙 SSOT
    └── templates/
```

### 배치 기준: "어디서 작업했나"가 아니라 "이 지식이 누구 것인가"

- 프로젝트에 종속된 사고의 흐름 → `projects/<프로젝트>/context/`
- 처음부터 범용적인 지식 (예: 스트리밍 프로토콜 비교) → 바로 `topics/`에 배치. 단, 어느 프로젝트 작업 중 얻었는지 출처 링크는 남김
- 캡처 시 Claude가 배치를 판단·제안하고 검토 단계에서 사람이 확정

### 컨텍스트 노트 스키마

```markdown
---
project: video-pipeline        # 기계용 — 플러그인이 파싱
date: 2026-07-22
author: haneol
type: decision                 # decision | exploration | work-log | meeting
topics: [영상-스트리밍, 인증]
status: approved               # draft | approved
---

# 인증 방식 결정

## 배경
(어떤 상황·요구에서 시작됐는지)

## 사고의 흐름
(무엇을 시도했고, 왜 버렸고, 왜 이 방향으로 갔는지)

## 결론
(결정 사항과 근거)

## 다음 단계 / 미해결
(남은 일, 미정 사항)

## 연관                        # 그래프용 — Obsidian이 그림
- 주제: [[영상-스트리밍]], [[인증]]
- 프로젝트: [[video-pipeline/_index|video-pipeline]]
- 관련 노트: [[2026-07-15-스트리밍-프로토콜-검토]]
```

**frontmatter와 본문 위키링크는 항상 쌍으로 생성**한다. frontmatter는 플러그인의 검색·큐레이션용, `## 연관`의 위키링크는 Obsidian 그래프 뷰용. Obsidian 그래프는 위키링크로만 그려지므로 이 컨벤션이 그래프 품질을 결정한다.

### 연관 관계 모델 (다대다)

- Obsidian 링크는 트리가 아닌 그래프 — 한 노트를 여러 프로젝트·topic이 링크 가능. 파일의 물리적 위치는 출처일 뿐, 소속은 링크가 정한다
- **topic 노트가 허브**: 여러 프로젝트의 노트가 topic 노트로 모여, repo 이름이 달라도 같은 주제면 그래프에서 한 덩어리로 보인다
- **topic 노트 승격**: 같은 주제가 여러 프로젝트에 반복 등장하면 topic 노트가 링크 허브를 넘어 정제된 지식 본문("정리된 지식" 섹션)을 담도록 증류한다. 원본 컨텍스트 노트들은 출처로 링크

## 5. 캡처 플로우

기록 단위는 세션이 아니라 **작업의 일단락**이다. 커밋은 그걸 자동 감지하는 가장 좋은 신호, 세션 종료는 놓친 것을 줍는 안전망.

### ① 주 트리거: 커밋 시점 (개발자)

1. 등록된 프로젝트에서 `git commit` 발생 → `commit-capture.sh` 훅이 Claude에게 "작업 일단락" 신호
2. Claude가 기록 가치를 판단 (오타 수정 등 사소한 커밋은 제안하지 않음)
3. 가치가 있으면 그 자리에서 제안: 사고의 흐름 초안 + 배치 제안 제시
4. 사용자 승인 → 즉시 검토·수정 → vault 반영 (같은 세션 내라 컨텍스트가 가장 신선하고 별도 API 비용 없음)
5. "나중에" → 대기열 등록만 하고 넘어감

### ② 보조 트리거: 세션 종료 (안전망)

- `session-capture.sh` 훅이 세션 종료 시 실행. 커밋 트리거로 이미 기록된 내용을 제외하고, 기록 안 된 의미 있는 컨텍스트(설계 논의, 조사 등 커밋 없는 작업)가 있으면 **로컬 대기열 파일에 등록만** 한다 — API 호출·vault 쓰기 없음
- `/kc:review` 실행 시: 대기열 세션들을 읽고 초안 생성 → 사람 검토·수정·승인 → vault 반영. 스킵하면 대기열에서 제거

### ③ 수동 기록: `/kc:log` (Claude Code 밖 작업)

- PPT·문서 등 외부 도구 작업의 일단락 시점에 작업자가 실행
- Claude가 인터뷰식으로 질문 (무슨 작업, 어떤 대안, 왜 그 결정, 막힌 점) → 구조화 노트 작성 → 검토 → vault 반영
- Claude 앱에서 작업한 경우 대화 내용을 붙여넣으면 같은 플로우로 처리

### ④ Inbox (비개발자)

- Obsidian으로 `inbox/`에 자유 형식 메모 (형식 규칙 없음 — 기여 부담 최소화)
- `/kc:curate`가 구조화 노트로 변환 + 배치 제안 → 검토 후 정식 위치로 이동

### 공통 원칙

- 어떤 경로든 **vault에 쓰기 전 반드시 사람 검토**
- 초안 생성 지시에 비밀정보(자격증명, 내부 주소 등) 제외 명시

## 6. Git 동기화 (자동)

팀원은 git 명령을 직접 다루지 않는다. vault에 쓰는 모든 명령(`/kc:log`, `/kc:review`, `/kc:curate`)이 자동으로:

1. 쓰기 전 `git pull --rebase`
2. 노트 생성/수정
3. `git commit`(내용을 설명하는 메시지 자동 작성) → `git push`

예외 처리:

- **충돌**: 노트는 대부분 "각자 새 파일 추가"라 충돌이 드묾. 같은 파일(예: `_index.md`) 충돌 시 Claude가 병합 시도, 애매하면 사용자에게 확인 — 조용히 한쪽을 버리지 않는다
- **push 실패** (네트워크 등): 커밋은 로컬에 보존, 다음 kc 명령 실행 시 먼저 push 재시도

`/kc:sync`의 역할: ① 쓰기 없이 최신 상태 받아보기, ② 꼬인 상태(방치된 충돌, 밀린 커밋) 진단·복구. 평상시엔 쓸 일이 없는 것이 정상.

## 7. 큐레이션 — `/kc:curate`

vault의 사서. 주기적으로(주 1회 정도, 아무나) 실행:

1. **Inbox 처리**: 자유 형식 메모 → 구조화 노트 변환 + 배치 제안
2. **연관 관계 정비**: frontmatter↔위키링크 불일치 수정, 깨진 링크 복구, `_index.md`·topic MOC 갱신
3. **승격 제안**: 여러 프로젝트에 반복 등장하는 주제 → topic 노트로 지식 증류 제안
4. **중복·노후 정리**: 겹치는 노트 병합 제안, 오래된 draft 정리
5. **결과 보고**: 변경 요약 제시 → **승인 후** 커밋 & push

### 컨벤션 SSOT: `vault/_meta/conventions.md`

폴더 구조·노트 스키마·링크 규칙을 기술. **플러그인의 모든 명령이 실행 전에 이 파일을 읽고 따른다.** 팀이 규칙을 바꾸면 이 파일만 수정 — 플러그인 업데이트 불필요.

## 8. 소비 (Soft Landing)

### `/kc:onboard <프로젝트>`

`_index.md` + 컨텍스트 노트 전체 + 연결된 topic 노트를 읽고 브리핑:

1. 프로젝트 배경
2. 주요 결정 타임라인 (왜 그렇게 됐는지)
3. 현재 상태와 미해결 사항
4. 연관 프로젝트/주제
5. 추천 읽기 순서 (노트 링크 포함)

브리핑 후 그 자리에서 후속 질문 가능.

### `/kc:ask <질문>`

frontmatter·본문 검색으로 관련 노트를 찾고 링크를 따라가며 맥락을 모아 답변. **답변에 항상 출처 노트 링크 명시** — 원문 검증 가능하게.

### Vault 자체 (제3의 소비 경로)

노트가 사람이 읽기 좋은 형식이므로, Obsidian으로 열어 그래프 뷰 탐색·topic 노트 읽기만으로도 온보딩이 된다. 노트 품질과 링크 컨벤션에 공을 들이는 이유.

## 9. 에러 처리 요약

| 상황 | 처리 |
|---|---|
| git 충돌 | Claude 병합 시도 → 애매하면 사용자 확인 |
| push 실패 | 로컬 커밋 보존, 다음 명령에서 재시도 |
| 비밀정보 | 초안 지시에서 제외 + 사람 검토에서 이중 확인 |
| vault 미설정 | 모든 명령이 감지 → `/kc:setup` 안내 |
| 사소한 커밋 | 기록 제안 자체를 생략 |
| 기록 거부/스킵 | 대기열에서 제거, 강제하지 않음 |

## 10. 테스트 전략

- 플러그인은 대부분 스킬(마크다운 지침) — **샘플 vault를 만들어 시나리오 워크스루**로 검증: 캡처(커밋 트리거·수동·inbox) → 동기화 → 큐레이션 → 온보딩·질의응답 전체 사이클
- 훅 스크립트(`commit-capture.sh`, `session-capture.sh`)는 단독 실행 테스트 (대기열 파일 등록, 사소한 커밋 필터 등)
- 충돌 시나리오: 두 clone에서 같은 `_index.md`를 수정해 병합 플로우 검증

## 11. 성공 기준

- 새 팀원이 `/kc:onboard` + topic 노트 열람만으로 프로젝트의 배경·결정·현재 상태를 파악할 수 있다
- 팀원이 git 명령을 직접 치지 않고도 vault가 동기화된다
- 커밋 시점 기록 제안이 작업 흐름을 방해하지 않는다 ("나중에"가 항상 가능)
- 비개발자가 형식 부담 없이 inbox로 기여할 수 있다
- vault를 Obsidian으로 열었을 때 그래프 뷰에서 topic 허브 중심의 연결 구조가 보인다
